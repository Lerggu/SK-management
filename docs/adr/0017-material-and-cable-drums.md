# ADR 0017 — Material batches, cable drums and QR labels

- Status: Accepted (V5, owner decisions 2 and 3)

## Material batches
- `material_batches` records a code, material, quantity and unit, plus optional links to a V4 delivery, a takt activity and a storage location.
- **Flow (`MATERIAL_FLOW`, pure):** RECEIVED → STORED → AT_WORKFACE → INSTALLED, with these extra moves:
  - RECEIVED → AT_WORKFACE;
  - AT_WORKFACE → STORED;
  - RETURNED from any open state.
  - INSTALLED and RETURNED are final.
- **Every status change writes a `material_movements` row:** from, to, location, activity, note, time and person.
  - Movements are append-only: a trigger blocks UPDATE and DELETE.
  - Creating the batch writes the first row.
- Moving to AT_WORKFACE or INSTALLED requires a takt activity.
- STORED requires a location.

## Cable drums (decision 2: metres for every pull)
- `cable_drums` records a code, manufacturer, cable type, original and remaining length, weight, dimensions, location, reserved activity, delivery, received date and inspection date.
- `cable_pulls` (append-only) records the metres, takt activity, date and person. A pull without an activity defaults to the drum's reserved activity.
- **Remaining length is never written directly:**
  - The trigger `cable_drums_guard` sets `remaining_m = original_length_m` on insert.
  - It refuses changes to the original length.
  - It refuses changes to `remaining_m` unless the change comes from `cable_pulls_apply`, which is marked by a transaction-local setting.
- `cable_pulls_apply` decrements the remaining length after each pull and sets the status to IN_USE, or to EMPTY at zero.
- `CHECK (remaining_m >= 0 AND remaining_m <= original_length_m)` makes a pull longer than what is left fail even under concurrent writes. The service also checks first, in tenths of a metre to avoid float drift.

## Traceability (acceptance criterion 3)
- Batches link a delivery to storage, the workface and installation, and every movement carries its activity.
- Pulls carry their activity.
- The takt activity page lists the activity's lifts, batches, drums and cable pulls, with metres pulled in total (`materialTraceService.activity`).

## QR labels (decision 3: generated by the system as PDF)
- `platform/labels` renders A4 sheets of 3 × 7 labels with `pdf-lib` and `qrcode`. It draws the QR modules as vector rectangles and calls no external service.
- **Each label carries:**
  - a QR code with an internal URL, `/c/<company>/scan/<opaque id>`, where the id is the record's UUIDv7;
  - the printed code, which is used for manual entry;
  - two short lines of description.
- A scan outside the system therefore reveals only the company slug and an opaque id.
- **Opening the URL requires a session and membership**, like any page. Unknown ids, other companies' ids, and records the member cannot see all return 404.
- The labels route is `GET /c/<company>/materials/labels?kind=drum|batch|accessory&siteId=…|ids=…`. It returns `application/pdf` with `Cache-Control: private, no-store`.

## Scanning on a phone (acceptance criterion 4)
- The scan view uses the browser's `BarcodeDetector` with the rear camera when available.
- **Fallback:** the user types the printed code. The input is case-insensitive, and a pasted URL or id also works.
- A detected value goes through the same server action as typed input, so resolution and authorization always happen on the server (`scanService.resolve`).

## Permissions
- `material.view` (all internal roles) and `material.manage` (CEO, PD, SM, SUP, LOG).
- The Client and Subcontractor templates get neither.
